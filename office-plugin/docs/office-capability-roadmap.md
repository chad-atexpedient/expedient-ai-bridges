# Office capability coverage roadmap

The product goal is for the add-in to behave like a skilled Office operator across Excel, Word, and PowerPoint: read the current file, reason with user-provided/M365 context, and directly perform the professional document work the user asked for.

This matrix distinguishes what is already implemented from what needs the next hardening pass. Office ribbon parity is not a single API switch; Office.js exposes different surfaces by host, platform, and update channel, so every new capability should follow the feature-detection pattern in `office-api-hardening.md`. See `office-missing-pieces-audit.md` for the deeper Word/Excel/PowerPoint gap audit and recommended next build slices.

## Known Office/API limitations to design around

- PowerPoint Office.js is thinner than Excel and Word. Some ribbon actions do not have stable task-pane APIs on all channels.
- Image insertion APIs vary by host/runtime. The current tools fail clearly when the installed Office build does not expose native image insertion.
- Some advanced document-generation work is better done server-side against Open XML packages, then opened/imported by the user, instead of trying to mutate a live document through Office.js only.
- Anthropic-compatible and OpenAI-compatible providers both get native tool loops. OpenAI-compatible streaming exists for non-tool responses; Anthropic streaming/tool-event streaming remains a production hardening target.

## Expansion rule

For every new Office capability:

1. Add a model tool schema in `src/lib/tools.ts`.
2. Add host/runtime filtering in `src/lib/capabilities.ts`.
3. Implement the action in `src/office/host.ts` or a server-side Open XML route when live Office APIs are insufficient.
4. Update provider host instructions so the model prefers real tools over manual instructions/placeholders.
5. Add tests that prove the tool is exposed only where intended.
6. Document any runtime fallback or production policy requirement.
