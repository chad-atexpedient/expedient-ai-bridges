Architecture & installation review

A local compatibility layer for enterprise AI.

Expedient AI Bridges lets OpenAI- and Anthropic-oriented desktop clients communicate with an Expedient/OpenAI-compatible upstream, while the packaged edition adds a Windows companion. Microsoft Office support is an optional plugin feature that consumes the same bridge capabilities.

Report v1.0 Windows 10/11

One upstream, multiple client dialects

01 — Executive summary

The short version

This is not an AI model and it does not run inference itself. It is a local gateway: it accepts requests in the formats expected by AI clients, maps models and message/tool structures, forwards them to a configured upstream AI service, then converts the response back to the calling client's format.

4001

OpenAI/Codex bridge

Local HTTP endpoint for Responses, Chat Completions, Models, and image-generation compatibility.

4002

Anthropic bridge

Local Anthropic Messages and token-count compatibility for Claude-oriented clients.

Plugin

Optional Office feature

An add-on task pane uses bridge-backed AI features in Excel, Word, and PowerPoint; it is not the core bridge.

Important provenance finding. The repository has now been synchronized with the exact v1.1.0 compiled bridge bundles and the complete Office plugin source tree, including tests, evaluations, build scripts, and lockfile. The published setup EXE remains the canonical native Windows package; a source-buildable cross-platform companion now lives under companion/; production supervision, signing, notarization, and installer/DMG assembly are the remaining release milestones.
02 — Product purpose

What it is—and is not

It is

  • A loopback-bound protocol adapter and request proxy.
  • A model-alias/router layer for a shared upstream catalog.
  • A stream/tool/message-format translator.
  • A resilient connector with retries, fallbacks, timeouts, capacity controls, and routing metrics.
  • In v1.1.0, a per-user Windows companion with tray/background behavior, bundled Node runtime, configuration UI, and Office integration.

It is not

  • A local large-language model or inference engine.
  • A credential-free service: an upstream key or forwarded client authorization is still required.
  • A VPN or general-purpose network tunnel.
  • A local inference engine or model host.
  • An MSI installation; registry evidence indicates a custom per-user executable installer.
03 — System architecture

End-to-end request path

Client/local componentBridge/translationRemote/service boundary

Trust boundary: the client-facing listeners are intended to stay on loopback. Prompts, document context, tool calls, and generated content can traverse the configured upstream connection. The bridge chooses compatibility and routing; the upstream performs inference.

04 — Protocol translation

How one request is transformed

Model aliasing

Recognized client model names are mapped to configured upstream model slots, preserving agent-oriented tool profiles where needed.

Tool translation

Responses tools and Anthropic tool-use blocks are normalized into OpenAI function tools, then reconstructed on return.

Streaming resilience

SSE is parsed and rebuilt; retry, connect/idle/total timeouts, non-stream fallback, and backpressure logic handle unreliable streams.

Current packaged generation

Installed v1.1.0 executable

Program: %LOCALAPPDATA%\Programs\Expedient AI Bridges State: %LOCALAPPDATA%\ExpedientAIBridges Start: ExpedientBridges.exe --background Runtime: bundled node.exe → bridge + Office services

The native companion owns install/uninstall and background startup. It bundles newer bridge files, Node 25.6.1, Office assets, and diagnostics.

User sign-in

The Startup shortcut launches ExpedientBridges.exe --background.

Companion initializes

It reads mutable configuration/state outside the program directory and starts child services with the bundled runtime.

Local services listen

OpenAI/Codex on 127.0.0.1:4001, Anthropic on 127.0.0.1:4002, and Office HTTPS workspace on localhost:3000 when enabled.

Clients connect

Desktop/CLI/Office callers use local URLs while credentials and routing direct traffic to the selected upstream.

Upgrade/uninstall

The per-user uninstall registry entry calls the same executable with --uninstall; no MSI product registration was found.

07 — Optional plugin feature

Office extends the bridge; it does not define it

The core product is the pair of protocol bridges on ports 4001 and 4002. The v1.1.0 package also carries an optional React/Vite Office task-pane plugin served locally over HTTPS. It consumes AI/provider functionality for Excel, Word, and PowerPoint and can be developed or deployed separately from the bridge core. The implementation filters tools against the active Office host and requirement sets so agents are not offered mutations the host cannot execute.

Excel plugin workflows

Workbook search; formula/dependency audit; range repair; tables, charts, pivots, formatting, validation, protection, images, and complete XLSX generation.

Word plugin workflows

Document audit and briefs; structured text, tables, styles, comments, controls, links, images, headers/footers, and complete DOCX generation.

PowerPoint plugin workflows

Deck audit; slides, diagrams, tables, shapes, layout operations, images and links; plus complete PPTX generation with speaker-note fallback.

Agent and skill layer

Dedicated Excel, Word, PowerPoint and Office-generalist agents combine with provider collaboration, research-context, native-provider, generation and demonstration skills.

Governance and artifact safety

Optional M365, file-context, web and image tools are policy-gated. Server controls cover production configuration, outbound targets, origin/auth, image validation, and structural QA for generated Office packages.

Validation evidence: 227 automated tests across 20 files pass alongside TypeScript checking and a production build. Availability still varies by Office host/runtime and tenant configuration.

Maturity boundary: M0 hardened development baseline with production integration contracts—not enterprise-ready or production-proven. Tenant infrastructure adapters, live identity/Graph validation, malware scanning, rendered Office QA, accessibility validation and pilot evidence remain external gates.

Branding discrepancy: packaged Office metadata still names the add-in “CTRL BYOK AI” / provider “CTRL,” while the Windows package is branded Expedient AI Bridges. This should be reconciled before a public release.

09 — Security review

Controls, exposure, and release risks

Observed strengths
  • Current packaged bridges refuse non-loopback binding unless explicitly overridden.
  • Configuration ACL is restricted to current user + SYSTEM.
  • Request-size, concurrency, and timeout limits reduce resource exhaustion.
  • New bridge validates tool policy and has structured error handling.
  • Office server includes origin checks, outbound-target allowlists, tenant capability policy, and production fail-closed configuration checks.
  • Office Entra validation checks issuer, audience, RS256 signature, time claims, and concrete tenant allowlists.
Release risks
  • Unsigned executable: v1.1.0 has no Authenticode signature, harming trust and SmartScreen reputation.
  • Packaging reproducibility: bridge and Office inputs are present, and the new companion builds from source, but CI does not yet assemble a signed setup or notarized DMG.
  • License omission: the package root lacks the source LICENSE; bundled dependencies need notices review.
  • Local bridge auth: loopback is the primary boundary; any local process can potentially call the listeners. Assess per-session tokens or named-pipe mediation.
  • Sensitive telemetry: routing logs/metrics must never capture prompt bodies, credentials, or tool arguments.
  • Certificate lifecycle: localhost Office TLS key/certificate generation, trust, rotation, and removal need documented guarantees.
Data-flow reminder. “Local bridge” does not mean “data stays local.” Request content is forwarded to the configured AI endpoint; Office features may also contact image, web, or Microsoft 365 endpoints when enabled. Public documentation should name these boundaries and retention responsibilities.

12 — GitHub readiness

Recommended publication sequence

Do not upload the current folder—or the installed Program directory—unchanged. First assemble a complete, sanitized, reproducible repository.

Identify the authoritative source tree

Use the recovered office-plugin/ source and current bridge payload as committed inputs; implement or recover the native companion project that produced commit 6635fb02….

Classify what may be published

Choose public vs private repository; confirm ownership, Expedient branding approval, endpoint disclosure, dependency licenses, and whether internal diagnostics belong.

Sanitize and harden

Add ignores; remove local config/logs/certs/build output; scan secrets; replace internal defaults where appropriate; add SECURITY, privacy/data-flow, support, and contribution documents.

Make builds reproducible

Pin toolchains/dependencies, document commands, add tests and CI, generate SBOM/checksums, and create signed Windows release artifacts from CI.

Create and push safely

Authenticate with the GitHub CLI/browser or a fine-grained, short-lived token entered through a secure prompt—not pasted into chat, source files, or remote URLs.

Credential safety: when we move to GitHub, do not send the access token in this conversation. Prefer gh auth login --web. If a token is necessary, use a fine-grained token limited to the single target repository, enter it only into the secure authentication prompt, then revoke it after the push.
